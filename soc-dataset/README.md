# Wazuh SOC Alert Triage Dataset (v4)

A labeled dataset of real Wazuh security alerts, generated by deliberately attacking a live, agent-monitored target VM with **real, industry-standard penetration testing tools** — not synthetic log lines, not even our own hand-written scripts alone. Built as the primary training/evaluation data for an AI-based SOC alert-triage decision engine (false-positive detection, severity/priority scoring, attack-chain/context awareness, response recommendation).

## What changed in v4 — and why it matters

Rounds 1–3 used hand-written curl loops and a handful of manual SSH attempts. That produced real alerts, but a narrow slice of what Wazuh can actually see, and a classifier trained only on that would learn to recognize *our specific scripts*, not general attack patterns. Round 4 fixes this by attacking the target with **actual tools a real attacker would use**:

- **`hydra`** — real SSH password-spraying with a 28-word realistic password list (not our own 5-6 guesses)
- **`gobuster`** — real directory brute-forcing using `dirb`'s bundled `common.txt` wordlist (4,600+ real paths)
- **`nikto`** — a full, real web vulnerability scanner (8,276 real requests: security header checks, outdated-software detection, Shellshock probes, and more)
- **`sqlmap`** — a real automated SQL injection tool, which **independently discovered and confirmed** the SQL injection on its own (correctly identified SQLite as the backend, found a working UNION-based payload) — we didn't tell it where the bug was

The payoff: Wazuh's own **native, mature rule engine** — not our custom rules — caught things our manual scripts never triggered, including correlation/frequency-based detections that only fire on realistic attack volume:

- `31151` *"Multiple web server 400 error codes from same source IP"* — Wazuh's built-in recon/scan detection (group: `web_scan,recon`)
- `31153` *"Multiple common web attacks from same source IP"* — Wazuh's own attack-chain correlation
- `31166`/`31168` *Shellshock attack attempt/detected*
- `31105`/`31154` *XSS attempt* / *Multiple XSS attempts from same source IP* — fired on nikto's real payloads, independent of our custom XSS rule
- `31171`/`31103` *SQL injection attempt* — fired on sqlmap's real payloads
- `40111`/`40112` *Multiple authentication failures* / *...followed by a success* — Wazuh's **native brute-force correlation engine**, which our earlier 5-6-attempt manual scripts were too small in volume to ever trigger
- `5763` *sshd: brute force trying to get access to the system*, `5551` *Multiple failed logins in a small period of time*

This is the single biggest quality improvement in the dataset: it demonstrates Wazuh's real detection capability under realistic attack volume, not just our custom rules.

## Files

| File | Description |
|---|---|
| `wazuh_soc_dataset.csv` | **Main labeled dataset.** 969 alerts, one row per alert, with our own ground-truth labels. Open directly in Excel/Sheets/pandas. |
| `wazuh_soc_dataset.jsonl` | Same 969 labeled alerts, one JSON object per line, full nested structure preserved. |
| `raw_alerts_full_soc-target.jsonl` | Unlabeled raw export of **every** alert ever generated by the target agent (13,480 records) — kept for full reproducibility/auditability. |
| `scripts/` | Every attack script across all four rounds, the vulnerable demo app, the three custom Wazuh rules, the real-tool wordlist builder, and the dataset-processing script. |

**Combined available labeled data**: 969 (ours, real-tool-generated) + 738 (supplementary) ≈ **~1,700 labeled alerts** for binary true-positive/false-positive training.

## Environment

- **Wazuh manager**: single-node install (indexer + manager + dashboard), Wazuh v4.9.2, on a GCP VM (`ctf-bugbounty`) — this VM also runs the attack tools (hydra, gobuster, nikto, sqlmap).
- **Target/agent**: a second GCP VM (`soc-target`), Wazuh agent v4.9.2, running nginx + a genuinely vulnerable Flask app (SQL injection, OS command injection, reflected XSS, SSTI→RCE), with syscheck extended to realtime-monitor `/home` and `/root`, plus multiple real and decoy accounts.
- **Custom detection content**: three custom rules (100100–100102, for command injection/XSS/SSTI) cover gaps in Wazuh's free ruleset for payload-based attacks that don't produce an HTTP error status. These work *alongside* Wazuh's native rules, not instead of them — v4 shows the native ruleset alone already covers a lot more ground than expected once given realistic traffic volume.

## Methodology

1. Environment-setup noise is excluded via time-window filtering across four scenario windows (documented in `scripts/process_dataset.js`).
2. Within those windows, alerts span: reconnaissance (port scanning, directory brute-forcing, vulnerability scanning), credential attacks (brute force — both low-volume manual and high-volume tool-driven, both ending in real compromises of decoy accounts), web application attacks (SQLi, XSS, command injection, SSTI/RCE, Shellshock probing), persistence (SSH key planting), privilege escalation (both failed and successful), anti-forensics (log tampering), and misconfiguration findings — plus substantial benign activity (legitimate logins, normal searches/browsing, routine admin actions) for realistic contrast.
3. **Downsampling**: nikto/gobuster's scanning generated an enormous volume of near-duplicate low-value 400-error entries (11,000+ raw). Including all of them would make the dataset 85%+ one repetitive category, which helps nobody. A **per-category cap of 120** was applied uniformly — every category (common or rare) is capped at the same limit, so no single high-volume category drowns out the higher-value rare ones. The true raw volume per category is fully visible in `raw_alerts_full_soc-target.jsonl` for anyone who wants the unsampled version.
4. Every alert was labeled with **ground truth we know for certain**, since we caused (or, for scanner noise, allowed) every event ourselves.

## Label schema

| Column | Meaning |
|---|---|
| `attack_category` | 26 distinct values — see the full list in `wazuh_soc_dataset.csv`. Highlights new in v4: `web_recon_scanning` (native Wazuh recon detection), `web_attack_chain_correlated` (native attack-chain correlation), `ssh_bruteforce_correlated` / `ssh_bruteforce_success_correlated` (native brute-force correlation), `web_attack_shellshock`, `web_attack_sqli`, `web_scan_noise_400` (low-value automated scanner noise — labeled `false` for true-positive). |
| `is_true_positive` | `true` = genuine security-relevant event; `false` = benign/routine/low-value noise |
| `severity` | `low`/`medium`/`high`/`critical` — derived from Wazuh's `rule.level`, with the highest-impact categories (successful compromises, persistence, RCE-class attacks, native attack-chain correlations) force-escalated to `critical` |
| `priority` | 1–5, derived from `is_true_positive` × `severity` |

**The core lesson this dataset teaches, reinforced further in v4**: the exact same Wazuh rule can mean completely different things depending on context (a benign admin login vs. a brute-forced compromise using the identical rule ID). v4 adds a second layer to this: **volume and correlation matter as much as content** — a single 400 error is noise (`web_scan_noise_400`, false positive); the *same* 400 errors repeated dozens of times from one source in a short window is a real recon signal (`web_recon_scanning`, true positive, and something Wazuh itself already knows how to detect). An AI decision engine needs to reason about both the individual event *and* its pattern over time — this dataset now has real examples of both.

## Class balance

- 969 total labeled alerts (own data) + 738 supplementary ≈ 1,700 combined
- 628 True Positive / 341 False Positive-or-noise in our own data (~65%/35% — more true-positive-heavy than earlier rounds since real attack tools generate genuine detections at volume; combine with the supplementary set, which skews the other way, for better overall balance)
- 26 distinct categories, all four severity levels well represented (medium 377, critical 286, low 182, high 124)

## Known limitations (v4)

- Several rare categories (successful SSTI/RCE, persistence, anti-forensics) still have single-digit counts — real, ground-truth-labeled, but not enough alone to train a per-category classifier without combining with more rounds or oversampling.
- JWT/header-based and XXE/POST-body attacks remain structurally invisible to access-log-only monitoring (unchanged from v3 — this is a monitoring-architecture limitation, not a data-collection gap).
- CSRF and race-condition attacks remain unrepresented for the same reason — they're indistinguishable from legitimate traffic at the log level by design.
- The per-category cap of 120 means the dataset is a *representative sample*, not the full raw volume — anyone wanting the true, unsampled distribution should work from `raw_alerts_full_soc-target.jsonl` directly.
- Labels were assigned via rule-based classification of Wazuh's own `rule.description`/`rule.groups`/`full_log` fields cross-checked against known ground truth — not independently reviewed by a third party.

## Reproducibility

Every alert came from a real, live Wazuh deployment attacked with real tools generating real network traffic. `scripts/` contains everything: the vulnerable app, all four rounds' attack scripts (including `tool_attack.sh` for the hydra/gobuster/nikto/sqlmap campaign and `make_wordlist.sh` for the password list), the three custom Wazuh rules, and `process_dataset.js` which turns raw `alerts.json` into the final labeled, capped CSV/JSONL — including the exact time windows and capping logic used.

## Anonymisation

To protect the authors' privacy, the following were masked before publication. Each replacement is applied consistently, so the number of distinct
sources, the structure of every log line and the model inputs are unchanged (the text-cleaning step used in the experiments already replaces IP
addresses by a placeholder).

| What | Replaced by |
|---|---|
| Public IP addresses of the authors' own workstation (SSH logins to the testbed) | Reserved documentation addresses `203.0.113.19` and `203.0.113.193` (RFC 5737) |
| Fingerprint of the authors' SSH public key | A synthetic fingerprint of the same shape |
| Linux account name of the testbed administrator | `maro` |
| Name of the administrator in the database schema (`analysts` table) | `Admin` |
| Home-directory paths of the deployment machine | `/home/maro/...` |

Not masked: addresses of scanners and attackers observed on the testbed, the testbed host names (`ctf-bugbounty`, `soc-target`) and the Google Cloud
internal addresses (`10.128.0.x`), which identify no person. A third-party supplementary alert set (Hugging Face `kholil-lil/wazuh-alerts`, MIT) was
explored during the project but is neither included nor used for any result in the paper.

**Effect on reruns.** The masking was applied after the experiments were run. The model inputs are identical in content (same terms, same counts), but the replacement names sort differently, so a few text-feature columns appear in a different order. Deterministic models (logistic regression) are unaffected; seed-dependent models (random forest, MLP, XGBoost and the ensemble) may differ from the paper in the last reported digit when rerun on the masked data. The paper's numbers were produced on the original, unmasked data.
